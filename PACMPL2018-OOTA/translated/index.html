    Towards Understanding the Costs of Avoiding Out-of-Thin-Air Results

    PEIZHAO OU, University of California, Irvine, USA

    欧培昭（PEIZHAO OU），美国加利福尼亚大学欧文分校，USA

    BRIAN DEMSKY, University of California, Irvine, USA

    布赖恩·德姆斯基 (BRIAN DEMSKY)，加利福尼亚大学欧文分校 (University of California, Irvine)，美国 (USA)

    Eliminating so-called "out-of-thin-air" (OOTA) results is an open problem with many existing programming language memory models including Java, C, and C++. OOTA behaviors are problematic in that they break both formal and informal modular reasoning about program behavior. Defining memory model semantics that are easily understood, allow existing optimizations, and forbid OOTA results remains an open problem. This paper explores two simple solutions to this problem that forbid OOTA results. One solution is targeted towards C/C++-like memory models in which racing operations are explicitly labeled as atomic operations and a second solution is targeted towards Java-like languages in which all memory operations may create OOTA executions. Our solutions provide a per-candidate execution criterion that makes it possible to examine a single execution and determine whether the memory model permits the execution. We implemented and evaluated both solutions in the LLVM compiler framework. Our results show that on an ARMv8 processor the first solution has no overhead on average and a maximum overhead of 6.3% on 43 concurrent data structures, and that the second solution has an average overhead of 3.1% and a maximum overhead of 17.6% on the SPEC CPU2006 C/C++ benchmarks.

    消除所谓的“凭空产生”(out-of-thin-air, OOTA)结果，是包括 Java、C 和 C++ 在内的许多现有编程语言内存模型 (memory model) 中的一个开放问题。OOTA 行为之所以成问题，是因为它们破坏了关于程序行为的形式化与非形式化模块化推理。定义一种易于理解、允许现有优化并禁止 OOTA 结果的内存模型语义，仍然是一个开放问题。本文探讨了该问题的两种简单解决方案，它们都禁止 OOTA 结果。一种解决方案面向类似 C/C++ 的内存模型，在这类模型中，竞争操作 (racing operations) 被显式标记为原子操作 (atomic operations)；另一种解决方案面向类似 Java 的语言，在这类语言中，所有内存操作都可能产生 OOTA 执行。我们的解决方案为每个候选执行 (candidate execution) 提供了一个判定准则，从而可以检查单个执行并确定内存模型是否允许该执行。我们在 LLVM 编译器框架中实现并评估了这两种解决方案。结果表明，在 ARMv8 处理器上，第一种解决方案在 43 个并发数据结构上平均没有开销，最大开销为 6.3%；第二种解决方案在 SPEC CPU2006 C/C++ 基准测试上平均开销为 3.1%，最大开销为 17.6%。

    1 INTRODUCTION

    Programming language memory models define the semantics of loads and stores in a multi-threaded program. Most programming language memory models guarantee sequential consistency for race free programs [Adve and Hill 1990]. This guarantee is fragile - a single data race voids the sequential consistency guarantee for the entire program. Indeed, programs with data races have undefined semantics under the C/C++11 memory model. While researchers have explored providing stronger guarantees to racy programs [Marino et al. 2011; Singh et al. 2012], these approaches may require hardware support to achieve competitive performance.

    编程语言内存模型 (memory models) 定义了多线程程序中加载 (loads) 和存储 (stores) 的语义。大多数编程语言内存模型 (memory models) 都保证无竞争程序 (race free programs) 的顺序一致性 (sequential consistency) [Adve and Hill 1990]。这一保证是脆弱的——单个数据竞争 (data race) 就会使整个程序的顺序一致性 (sequential consistency) 保证失效。事实上，在 C/C++11 内存模型 (memory model) 下，具有数据竞争 (data races) 的程序具有未定义语义。尽管研究人员已经探索了为有竞争程序 (racy programs) 提供更强保证的方法 [Marino et al. 2011; Singh et al. 2012]，但这些方法可能需要硬件支持才能实现有竞争力的性能。

    Memory models assign undefined semantics to racy programs as data races violate assumptions made by compiler optimizations. For existing compilers, assigning meaningful semantics to racy programs is extremely complicated. The language semantics must capture behaviors that arise from both compiler and processor optimizations.     A key challenge in programming language memory models is prohibiting out-of-thin-air behaviors or satisfaction cycles. This problem is well known [Batty et al. 2013, 2015a; Manson et al. 2005; Pichon-Pharabod and Sewell 2016] and has been described in detail [Boehm and Demsky 2014]. Figure 1 presents an execution that real processors produce. A processor might reorder the store of 42 to \( \mathrm{x} \) in Thread 2, Thread 1 can then read the value42from \( \mathrm{x} \) and store it in \( \mathrm{y} \) , and finally Thread 2 can load 42 from y.

    编程语言内存模型 (memory models) 中的一个关键挑战是禁止无中生有 (out-of-thin-air) 行为或满足环 (satisfaction cycles)。这个问题已广为人知 [Batty et al. 2013, 2015a; Manson et al. 2005; Pichon-Pharabod and Sewell 2016]，并且已有详细描述 [Boehm and Demsky 2014]。图 1 展示了真实处理器会产生的一种执行。处理器可能会在线程 2 中重排将 42 存储到 \( \mathrm{x} \) 的操作，随后线程 1 可以从 \( \mathrm{x} \) 读取值42并将其存储到 \( \mathrm{y} \) 中，最后线程 2 可以从 y 中加载 42。

    Figure 2 presents an out-of-thin-air example with the same reads-from \( {}^{1} \) relationship between loads and stores as the previous example. If both loads read from the subsequent stores, the C and C++ memory model formalism admits an execution in which r1=r2=42 (or any other value), conjuring the value of 42 "out of thin air". The key difference between these two examples is that in the problematic example, the stores depend on the previous loads.

    图 2 展示了一个无中生有 (out-of-thin-air) 的示例，它与前一个示例在加载 (loads) 和存储 (stores) 之间具有相同的 reads-from \( {}^{1} \) 关系。如果两个加载 (loads) 都从后续的存储 (stores) 中读取，C 和 C++ 内存模型 (memory model) 形式主义 (formalism) 允许一种执行，其中 r1=r2=42（或任何其他值），从而“无中生有”地构造出值 42。这两个示例之间的关键区别在于，在这个有问题的示例中，存储 (stores) 依赖于先前的加载 (loads)。

    Note that if we directly write these examples in assembly, no processor will produce the problematic results in Figure 2. Processors preserve a notion of dependency - a processor core will not make a speculative store visible to other cores. Compilers in general do not preserve dependencies - compiler optimizations can easily optimize away dependencies (e.g., an if statement in which both branches store the same value to the same variable). Compiler optimizations conspire with relaxed hardware implementations to create the problem.

    请注意，如果我们直接用汇编 (assembly) 编写这些示例，那么任何处理器 (processor) 都不会产生图 2 中有问题的结果。处理器 (processor) 会保留某种依赖关系 (dependency) 的概念——处理器核心 (processor core) 不会让推测性存储 (speculative store) 对其他核心 (cores) 可见。编译器 (compilers) 通常不会保留依赖关系 (dependencies)——编译器优化 (compiler optimizations) 很容易将依赖关系 (dependencies) 优化掉（例如，在一个 if 语句中，两个分支都将相同的值存储到同一个变量）。编译器优化 (compiler optimizations) 与宽松的硬件实现 (relaxed hardware implementations) 相互作用，从而造成了这个问题。

An optimizing compiler may discover that the load \( {r1} = x \) in Thread 1 will always return the value of 42 no matter whether the conditional branch is taken or not. Hence it can replace the store y=r1 with \( y = {42}^{2} \) , and then through the same reads-from relationship between loads and stores as Figure 2, the execution in which r1=r2=42 is allowed. While some researchers argue that this is OOTA behavior and should be disallowed, other researchers may argue that this is legitimate behavior because the value of 42 in this example arises from the untaken branch.

    尽管人们一致认为图 2 表示凭空出现 (OOTA) 行为，但对 OOTA 的精确定义仍存在争议。请考虑图 3 所示的示例（引自 Boehm and Demsky [2014]）。优化编译器 (optimizing compiler) 可能会发现，线程 1 中的加载 \( {r1} = x \) 无论条件分支是否被采用，都会始终返回值 42。因此，它可以将存储 y=r1 替换为 \( y = {42}^{2} \)，然后通过与图 2 中加载和存储之间相同的 reads-from 关系，允许出现 r1=r2=42 的执行。尽管一些研究人员认为这是凭空出现 (OOTA) 行为，因此应当被禁止，但另一些研究人员可能会认为这是合法行为，因为在这个例子中，值 42 来自未被采用的分支。

    1.2 Consequences

    As previously noted [Batty et al. 2013; Boehm and Demsky 2014], allowing out-of-thin-air results is disastrous. Serious issues of allowing OOTA results include:

    如前所述 [Batty et al. 2013; Boehm and Demsky 2014]，允许凭空产生结果 (out-of-thin-air results) 是灾难性的。允许凭空产生结果 (OOTA results) 的严重问题包括：

    (1) OOTA Results Break Formal Modular Reasoning: As noted by Batty et al. [2013], OOTA executions can break certain types of compositional reasoning about programs. In particular, even if the guarantees provided by each component satisfy the assumptions of all other components, OOTA results allow executions in which two components mutually violate their own guarantees and thus violate the assumptions of the other component (circularly justifying their violation of their guarantees).

    (1) OOTA 结果破坏形式化模块化推理：正如 Batty et al. [2013] 所指出的，OOTA 执行 (execution) 会破坏关于程序的某些类型的组合式推理 (compositional reasoning)。特别是，即使每个组件 (component) 提供的保证 (guarantees) 满足所有其他组件的假设 (assumptions)，OOTA 结果仍然允许这样的执行：两个组件相互违反各自的保证，从而违反另一个组件的假设（以循环方式为其对自身保证的违反进行正当化）。

    In languages that allow OOTA results, compositionality requires proving that each component in a composition is non-interfering (i.e., that it does not write to the memory locations of other components). Indeed, some analyses and tools that are based on the C/C++ memory model either simply assume the non-existence of OOTA behavior or require a stronger version of the C/C++ memory model that prohibits OOTA behavior [Kokologiannakis et al. 2017; Meshman et al. 2015; Norris and Demsky 2013; Ou and Demsky 2015].

    在允许 OOTA 结果的语言中，可组合性 (compositionality) 要求证明组合中的每个组件都是非干扰的 (non-interfering)（即，它不会写入其他组件的内存位置）。事实上，一些基于 C/C++ 内存模型的分析与工具，要么直接假设不存在 OOTA 行为，要么要求采用禁止 OOTA 行为的更强版本 C/C++ 内存模型 [Kokologiannakis et al. 2017; Meshman et al. 2015; Norris and Demsky 2013; Ou and Demsky 2015]。

    (2) OOTA Results Break Informal Modular Reasoning: While developers rarely formally prove their software correct, OOTA results can even break informal reasoning about programs. Indeed, for many programs it may be necessary to avoid including accesses to relaxed atomics in the code base. For example, simply exposing an interface to relaxed stores to a virtual machine interpreter is likely sufficient to allow OOTA results that can produce arbitrary executions.

    (2) OOTA 结果打破了非形式化模块化推理：虽然开发者很少正式证明其软件的正确性，但 OOTA 结果甚至可能打破关于程序的非形式化推理。事实上，对于许多程序而言，可能有必要避免在代码库中包含对宽松原子操作 (relaxed atomics) 的访问。例如，仅仅向虚拟机解释器暴露一个到宽松存储 (relaxed stores) 的接口，就很可能足以允许产生任意执行的 OOTA 结果。

    (3) OOTA Results Can Affect Race-Free Computations: OOTA results can induce race-free computations to produce surprising results. The following example is courtesy of Sarita Adve:

    （3）凭空出现（OOTA）结果可能影响无竞态（race-free）计算：凭空出现（OOTA）结果可能诱导无竞态（race-free）计算产生令人惊讶的结果。以下示例由萨丽塔·阿德维（Sarita Adve）提供：

    Thread 1Thread 2
    if (x) y=1;if (y) x=1;

    Even with \( x = y = 0 \) initially, OOTA results allow this computation to set both \( x \) and \( y \) to 1 .

    即使最初 \( x = y = 0 \)，OOTA 结果仍允许该计算将 \( x \) 和 \( y \) 都设为 1。

    1.3 Potential Solutions

    Researchers have proposed several different basic approaches to solving the out-of-thin-air problem. We next discuss the different basic approaches. These approaches fall into two primary categories. The first category attempts to eliminate the problem by changing the memory model specification without significant changes to the compiler and the second category attempts to eliminate the problem by providing stronger guarantees.

    研究人员 (Researchers) 已经提出了几种不同的解决凭空出现 (out-of-thin-air) 问题的基本方法 (approaches)。接下来我们讨论这些不同的基本方法。这些方法分为两个主要类别。第一类试图通过修改内存模型规范 (memory model specification) 来消除该问题，而不对编译器 (compiler) 进行重大修改；第二类则试图通过提供更强的保证 (guarantees) 来消除该问题。

    1.3.1 Approaches that Primarily Affect the Language Specification.

    1.3.1 主要影响语言规范 (language specification) 的方法 (Approaches)。

    Precisely Specifying the Effects of Existing Optimizations: Forbidding OOTA behaviors by precisely specifying the effects of existing optimizations is one potential solution. This approach is tempting as it incurs no runtime overheads and requires no modifications to either compilers or processors. Researchers have proposed event-structures-based memory models [Jeffrey and Riely 2016; Pichon-Pharabod and Sewell 2016] that were later shown not to be compiled to ARM without additional fences in some cases [Kang et al. 2017].

    精确规定现有优化 (optimizations) 的效果：通过精确规定现有优化 (optimizations) 的效果来禁止 OOTA 行为 (behaviors) 是一种潜在的解决方案。这种方法很有吸引力，因为它不会产生运行时开销 (runtime overheads)，也不需要对编译器 (compilers) 或处理器 (processors) 进行任何修改。研究人员提出了基于事件结构 (event-structures-based) 的内存模型 (memory models) [Jeffrey and Riely 2016; Pichon-Pharabod and Sewell 2016]，但后来证明，在某些情况下，如果没有额外的栅栏 (fences)，这些模型无法被编译到 ARM [Kang et al. 2017]。

    Attempts at forbidding OOTA executions by precisely specifying the effects of optimizations have to date yielded complicated memory models. Indeed, Batty et al. [2015b] show that there is no per-candidate-execution solution to the problem. For example, Kang et al. [2017] propose a memory model based on a semantics that claims to resolve the OOTA problem, and the proof of its compilation correctness has been shown by Podkopaev et al. [2017]. While this approach can potentially solve the OOTA problem, a less complex but slightly stronger memory model may still be desirable if the overhead is acceptably small.

    迄今为止，试图通过精确规定优化 (optimizations) 的效果来禁止 OOTA 执行 (executions) 的做法，已经产生了复杂的内存模型 (memory models)。事实上，Batty et al. [2015b] 表明，对该问题不存在任何按候选执行 (per-candidate-execution) 的解决方案。例如，Kang et al. [2017] 提出了一种基于语义 (semantics) 的内存模型 (memory model)，并声称能够解决 OOTA 问题，而其编译正确性 (compilation correctness) 的证明已由 Podkopaev et al. [2017] 给出。尽管这种方法有可能解决 OOTA 问题，但如果开销 (overhead) 足够小，那么一种复杂性更低但略强一些的内存模型 (memory model) 可能仍然是可取的。

    The Java Memory Model also attempted this approach [Manson et al. 2005], but the approach has since shown to be unsound with respect to standard compiler optimizations [Ševčík and Aspinall 2008]. Moreover, the JMM is extremely complicated for both compiler developers and application developers to understand. It is also complicated to use the constraints placed on OOTA executions by the JMM to prove correctness properties for concurrent programs. Indeed, merely verifying whether the JMM allows a given concrete execution is undecidable [Botinčan et al. 2010].

    Java 内存模型 (Memory Model) 也曾尝试这种方法 [Manson et al. 2005]，但此后该方法已被证明相对于标准编译器优化而言是不可靠的 [Ševčík and Aspinall 2008]。此外，JMM 对于编译器开发者和应用开发者来说都极其复杂，难以理解。利用 JMM 对 OOTA 执行施加的约束来证明并发程序的正确性属性也很复杂。事实上，仅仅验证 JMM 是否允许某个给定的具体执行就是不可判定的 [Botinčan et al. 2010]。

    Case-Based Approaches: Another approach is to constrain the usage of atomics to specific cases and then provide simple semantics for those cases. The most well known example of this approach is the classic "data race freedom implies sequential consistency" memory model used by most multithreaded programming languages [Adve and Hill 1990]. In this model, if there is no sequentially consistent execution with a data race, then the system guarantees that all executions are sequentially consistent. Other work enumerates common use cases for relaxed atomics and provides semantics for those use cases [Sinclair et al. 2017].

    基于案例的方法 (Case-Based Approaches)：另一种方法是将原子操作 (atomics) 的使用限制在特定情形中，然后为这些情形提供简单的语义。该方法最广为人知的例子是大多数多线程编程语言使用的经典“数据竞争自由 (data race freedom) 蕴含顺序一致性 (sequential consistency)”内存模型 [Adve and Hill 1990]。在该模型中，如果不存在带有数据竞争 (data race) 的顺序一致 (sequentially consistent) 执行，那么系统保证所有执行都是顺序一致 (sequentially consistent) 的。其他工作则枚举了宽松原子操作 (relaxed atomics) 的常见使用案例，并为这些使用案例提供语义 [Sinclair et al. 2017]。

    There are two basic challenges with this approach: (1) memory model developers must ensure that the cases handled cover the important usage scenarios and (2) bugs can produce behaviors that fall outside the well defined cases and then the memory model may provide little or no guarantees as to the program's behaviors.

    这种方法存在两个基本挑战：(1) 内存模型开发者必须确保所处理的情况涵盖重要的使用场景；以及 (2) 缺陷 (bugs) 可能产生落在明确良定义情况之外的行为，此时内存模型对于程序行为可能几乎不提供任何保证，甚至完全不提供保证。

    1.3.2 Approaches that Provide Stronger Guarantees.

    Approach 1: Forbid Load-Store Reordering: A conceptually simple approach to forbidding OOTA executions is to forbid load-store reordering [Boehm and Demsky 2014; Lahav et al. 2017]. Precisely, the memory model requires that sequence-before \( \cup \) reads-from is acyclic. This greatly simplifies the memory model for both compiler and application developers, but can potentially incur significant runtime costs.

    方法 1：禁止加载-存储 (load-store) 重排序：一种在概念上简单的禁止 OOTA 执行的方法，是禁止加载-存储 (load-store) 重排序 [Boehm and Demsky 2014; Lahav et al. 2017]。准确地说，内存模型 (memory model) 要求 sequence-before \( \cup \) reads-from 是无环的。这极大地简化了编译器和应用程序开发者的内存模型 (memory model)，但也可能带来显著的运行时成本。

    Implementing this approach requires changes to compiler optimizations and the potential generation of a fence-like operation. The cost of this approach depends on both the details of the memory model and the hardware architecture. While x86 processors already provide this behavior without requiring fences, architectures like ARM or PowerPC may incur higher overheads. We believe that this approach is likely to be acceptable for memory models like C/C++11 as it only affects relaxed loads and stores \( {}^{3} \) . However, this approach affects all loads and stores in Java programs, and thus is likely to be less acceptable in the context of Java.

    实现这种方法需要对编译器优化进行修改，并可能生成一种类似栅栏 (fence)-的操作。该方法的成本取决于内存模型 (memory model) 和硬件架构 (hardware architecture) 的具体细节。尽管 x86 处理器已经提供了这种行为而无需栅栏 (fence)，但像 ARM 或 PowerPC 这样的架构可能会产生更高的开销。我们认为，这种方法对于像 C/C++11 这样的内存模型 (memory model) 来说很可能是可以接受的，因为它只影响宽松加载 (relaxed loads) 和宽松存储 (relaxed stores) \( {}^{3} \) 。然而，这种方法会影响 Java 程序中的所有加载 (loads) 和存储 (stores)，因此在 Java 的语境下可能较难被接受。

    Approach 2: Preserve Dependencies: Earlier work suggested but did not implement one potential approach to forbidding OOTA executions - require the compiler to preserve a simple, syntactic notion of dependency [Boehm and Demsky 2014]. Effectively, this approach provides a syntactic definition for a dependency relationship and then requires that dependency \( \cup \) reads-from is acyclic. This is a strictly weaker guarantee than the previous approach. It is worth noting that the Linux kernel memory model does not have out-of-thin-air values because it essentially respects syntactic dependencies as hardware does [Alglave et al. 2018]. McKenney et al. [2016] have proposed an approach based on preserving semantic dependencies rather than syntactic dependencies. For example, they allow reducing an expression with syntactic dependency to a constant if it is known to always result in that constant value (e.g., reducing "r1=x*0" to "r1=0"). This trades off the simplicity of the memory model specification for the degree of compiler optimizations that are allowed. In this paper, we explore an approach of preserving syntactic dependencies.

    方法 2：保留依赖关系：早期工作提出了但并未实现一种可能的禁止 OOTA 执行的方法——要求编译器保留一种简单的、句法上的依赖 (dependency) 概念 [Boehm and Demsky 2014]。实际上，这种方法为依赖关系提供了一个句法定义，然后要求依赖 \( \cup \) reads-from 是无环的。这比前一种方法提供了严格更弱的保证。值得注意的是，Linux 内核内存模型 (memory model) 不存在凭空产生 (out-of-thin-air) 的值，因为它本质上像硬件那样尊重句法依赖 (syntactic dependencies) [Alglave et al. 2018]。McKenney et al. [2016] 提出了一种基于保留语义依赖 (semantic dependencies) 而非句法依赖 (syntactic dependencies) 的方法。例如，如果已知一个具有句法依赖的表达式总是会得到某个常量值，他们允许将其化简为一个常量（例如，将 "r1=x*0" 化简为 "r1=0"）。这在内存模型规范 (memory model specification) 的简洁性与允许的编译器优化程度之间进行了权衡。在本文中，我们探索一种保留句法依赖 (syntactic dependencies) 的方法。

    \( {}^{3} \) Under C/C++11, non-atomic loads and stores cannot race, or the program has no semantics. Thus, reordering cannot be observed.

    \( {}^{3} \) 在 C/C++11 标准下，非原子（non-atomic）加载（loads）和存储（stores）不能发生竞争（race），否则程序将不具有语义（semantics）。因此，重排序（reordering）无法被观察到。

    While this approach does not require the addition of any extra fence instructions, it does constrain the optimizations performed by the compiler. The primary concern with this approach is that the overheads were previously unknown and feared to be high.

    尽管这种方法不需要添加任何额外的 栅栏指令 (fence instructions)，但它确实限制了 编译器 (compiler) 所执行的 优化 (optimizations)。这种方法的主要担忧在于，此前其 开销 (overheads) 尚不明确，并且人们担心其会很高。

    2 MEMORY MODEL EXTENSIONS THAT DISALLOW OOTA BEHAVIORS

    In this section, we first discuss a dependency-preserving memory model that disallows out-of-thin-air behaviors by defining a notion of dependency and preserving it. While it is desirable that we formalize this memory model in the context of an existing programming language, e.g., C/C++ or Java, both the C/C++ and Java languages are complex and the formalization would exceed the scope of this paper.     We formalize the program execution state as the tuple \( \delta = \langle N, V,{dep}, D,{PC},{FD}\rangle \) , where \( N \) represents a computational node (e.g., an expression or statement), \( V \) represents a mapping from an expression to its concrete value, dep represents a dependency set, which is a subset of the Cartesian product of the load set and store set in an execution. For example, \( \left( {l, s}\right) \in {dep} \) " means that store \( s \) depends on load \( l;D \) represents a dependency mapping from an expression to the set of loads the expression depends on, \( {PC} \) represents the set of loads on which the current instruction has explicit control dependency, and FD represents the set of loads on which future stores should depend. Essentially, the rules of our semantics focus on recording which loads an expression or statement depends on in each step of the execution, and when we finish executing the program, the final result is recorded in dep - the complete dependency relation between loads and stores in the execution. The details of dependency rules follow:

    我们将程序执行状态形式化为元组 \( \delta = \langle N, V,{dep}, D,{PC},{FD}\rangle \)，其中，\( N \) 表示一个计算节点 (computational node)（例如，一个表达式或语句），\( V \) 表示从表达式到其具体值的映射，dep 表示一个依赖集合 (dependency set)，它是一次执行中加载集合 (load set) 与存储集合 (store set) 的笛卡尔积的子集。例如，\( \left( {l, s}\right) \in {dep} \) 表示存储 \( s \) 依赖于加载 \( l \)；\( D \) 表示从表达式到该表达式所依赖的加载集合的依赖映射 (dependency mapping)，\( {PC} \) 表示当前指令具有显式控制依赖的加载集合，\( FD \) 表示未来的存储应当依赖的加载集合。本质上，我们语义的规则聚焦于记录在执行的每一步中一个表达式或语句依赖于哪些加载；当我们完成程序执行时，最终结果记录在 dep 中——即该次执行中加载与存储之间完整的依赖关系。依赖规则 (dependency rules) 的细节如下：

    (1) Expressions: In general, an expression has data dependency on its subexpressions, meaning that the expression depends on whatever loads its subexpressions depend on. In our operational semantics, an expression \( E \) can be reduced to a pair \( \langle \mathcal{V},\mathcal{D}\rangle \) , in which \( \mathcal{V} \) represents the concrete value to which \( E \) is evaluated, and \( \mathcal{D} \) represents the set of loads \( E \) depends on. The Const.Expr rule means a constant numeral is evaluated to itself and does not depend on any loads; the Var.Expr rule means a variable var retrieves its concrete value recorded in \( V \) and its dependency set recorded in D; the Unary.Expr and Binary.Expr rules are specifically for unary and binary expressions, respectively; the Load.Expr rule means that a load expression has data dependency on its address. It is important to note that in the dependency relation we define, loads are the sources and stores are the sinks. More specifically, given a load instruction \( l \) and its address \( {Addr} \) (which depends on \( \mathcal{D} \) ), \( l \) depends on the union of \( \mathcal{D} \) and \( l \) itself, denoted as fresh_load (since \( l \) becomes the source in the dependency relation after we execute the load). In the Load.Expr rule," \( {\mathcal{V}}_{\text{ load }} = \operatorname{load}\left( {\mathcal{V}}_{\text{ Addr }}\right) \) " means reading the value from address \( {\mathcal{V}}_{\text{ Addr }} \) and assigning it to \( {\mathcal{V}}_{\text{ load }} \) .

    （1）表达式 (expression)：一般而言，一个表达式 (expression) 对其子表达式 (subexpressions) 存在数据依赖 (data dependency)，这意味着该表达式 (expression) 依赖于其子表达式 (subexpressions) 所依赖的任何加载 (loads)。在我们的操作语义 (operational semantics) 中，一个表达式 (expression) \( E \) 可以被归约为一个二元组 \( \langle \mathcal{V},\mathcal{D}\rangle \)，其中 \( \mathcal{V} \) 表示 \( E \) 被求值到的具体值 (concrete value)，而 \( \mathcal{D} \) 表示 \( E \) 所依赖的加载 (loads) 集合。Const.Expr 规则表示一个常量数字 (constant numeral) 被求值为其自身，并且不依赖于任何加载 (loads)；Var.Expr 规则表示一个变量 (variable) var 获取记录在 \( V \) 中的其具体值 (concrete value) 以及记录在 D 中的其依赖集合 (dependency set)；Unary.Expr 和 Binary.Expr 规则分别专门对应一元表达式 (unary expressions) 和二元表达式 (binary expressions)；Load.Expr 规则表示一个加载表达式 (load expression) 对其地址 (address) 存在数据依赖 (data dependency)。需要特别注意的是，在我们定义的依赖关系 (dependency relation) 中，加载 (loads) 是源 (sources)，而存储 (stores) 是汇 (sinks)。更具体地说，给定一条加载指令 (load instruction) \( l \) 及其地址 (address) \( {Addr} \)（其依赖于 \( \mathcal{D} \)），\( l \) 依赖于 \( \mathcal{D} \) 与 \( l \) 自身的并集，记作 fresh_load（因为在我们执行该加载 (load) 之后，\( l \) 在依赖关系 (dependency relation) 中成为源 (source)）。在 Load.Expr 规则中，“\( {\mathcal{V}}_{\text{ load }} = \operatorname{load}\left( {\mathcal{V}}_{\text{ Addr }}\right) \)”表示从地址 \( {\mathcal{V}}_{\text{ Addr }} \) 读取该值，并将其赋给 \( {\mathcal{V}}_{\text{ load }} \)。

    (2) Assignments: For an assignment statement "var \( = E \) ", the left-hand side variable \( {var} \) has data dependency on the right-hand side expression \( E \) . Thus, the Assignment rule assigns the concrete value of \( E \) to var and also passes the dependencies of \( E \) to var.

    （2）赋值 (Assignments)：对于赋值语句 “var \( = E \)”，左侧变量 \( {var} \) 对右侧表达式 \( E \) 具有数据依赖 (data dependency)。因此，赋值规则 (Assignment rule) 将 \( E \) 的具体值赋给 var，同时也将 \( E \) 的依赖关系传递给 var。

    (3) Stores: For a store statement \( s \) ,"store Addr, Val", where the address Addr has dependency on load set \( {\mathcal{D}}_{\text{ Addr }} \) and the storing value has dependency on load set \( {\mathcal{D}}_{\text{ Val }}, s \) has data dependency on \( {\mathcal{D}}_{\text{ Addr }} \cup {\mathcal{D}}_{\text{ Val }} \) . For example, in 6 (a), since the storing value r2 has data dependency on "r1 = load &x", so store "store &y, r2" depends on "r1 = load &x". In addition, s should depend on the set of loads on which it has explicit control dependency, which in our operational semantics is recorded in PC. For example, in 6 (b), store "store &y, 1" depends on "r1 = load &x" because of explicit control dependency.

    (3) 存储 (Stores)：对于一个存储语句 \( s \)，即“store Addr, Val”，其中地址 Addr 依赖于加载集合 \( {\mathcal{D}}_{\text{ Addr }} \)，而被存储的值依赖于加载集合 \( {\mathcal{D}}_{\text{ Val }} \)，则 \( s \) 在数据上依赖于 \( {\mathcal{D}}_{\text{ Addr }} \cup {\mathcal{D}}_{\text{ Val }} \)。例如，在 6 (a) 中，由于被存储的值 r2 在数据上依赖于“r1 = load &x”，因此存储“store &y, r2”依赖于“r1 = load &x”。此外，\( s \) 还应依赖于它具有显式控制依赖的加载集合，在我们的操作语义 (operational semantics) 中，这被记录在 PC 中。例如，在 6 (b) 中，存储“store &y, 1”依赖于“r1 = load &x)”，这是由于显式控制依赖。

    However, it is not sufficient to only consider explicit data and control dependencies. Consider the question of whether the last store "store &y, r2" depends on the first load “r1 = load &x” in Figure 6 (c). At first glance, it may appear to be that “store &y, r2” only depends on "r2 = load &z" but is independent of "r1 = load &x" since "store &y, r2" does not have an explicit data dependency or control dependency on "r1 = load &x". However, if we consider the question of what value the memory location y will hold at the end of the execution (assuming z=1 before each execution), we can see that the answer becomes either the value 1 or 0 depending on whether r1 points to the memory address of \( \mathrm{z} \) , which means "store &y, r2" actually depends on "r1 = load &x". Technically speaking, if we can tell by some static analysis (e.g., some sort of points-to analysis) that r1 always points to a different memory address than z, then "store &y, r2" does not depend on "r1 = load &x". However, if we rely on such analysis in our rules, we will end up with an extremely complicated dependency notion; moreover, the fact that C/C++ allows pointer arithmetics and pointer conversions would further complicate the dependency notion because the precise addresses of loads and stores may not be always known. Hence, instead of incorporating the details of the points-to analysis in our definition of dependency, we take a very conservative approach. In our semantics, if the address of a store depends on some load, then we require that all subsequent stores also depend on that load. We refer to this type of dependency as an address dependency. Back to the example shown in Figure 6 (c), we simply conservatively say that the store "store &y, r2" depends on the load "r1 = load &x", even if the compiler knows r1 will never point to the address of z. As a result, in our implementation, if the compiler wishes to reorder a store \( {s}^{\prime } \) ("store &y, r2" in this example) up above another store \( s \) ("store r1,0 " in this example), it has to make \( {s}^{\prime } \) depend on any loads that the address of \( s \) depends on ("r1 = load &x" in this example).

    然而，仅仅考虑显式数据依赖 (data dependency) 和控制依赖 (control dependency) 还不够。考虑图 6 (c) 中最后一条存储 “store &y, r2” 是否依赖于第一条加载 “r1 = load &x” 的问题。乍一看，似乎 “store &y, r2” 只依赖于 “r2 = load &z”，而独立于 “r1 = load &x”，因为 “store &y, r2” 对 “r1 = load &x” 不具有显式数据依赖 (data dependency) 或控制依赖 (control dependency)。然而，如果我们考虑在执行结束时内存位置 y 将保存什么值这一问题（假设每次执行之前 z=1），就会发现答案会变成 1 或 0，这取决于 r1 是否指向 \( \mathrm{z} \) 的内存地址，这意味着 “store &y, r2” 实际上依赖于 “r1 = load &x”。从技术上讲，如果我们能够通过某种静态分析 (static analysis)（例如某种指向分析 (points-to analysis)）判断 r1 总是指向与 z 不同的内存地址，那么 “store &y, r2” 就不依赖于 “r1 = load &x”。然而，如果我们在规则中依赖这种分析，就会得到一种极其复杂的依赖概念；此外，C/C++ 允许指针运算 (pointer arithmetics) 和指针转换 (pointer conversions) 这一事实会进一步使依赖概念复杂化，因为加载和存储的精确地址可能并不总是已知。因此，我们并不将指向分析 (points-to analysis) 的细节纳入依赖定义中，而是采取一种非常保守的方法。在我们的语义中，如果某个存储的地址依赖于某个加载，那么我们要求所有后续存储也都依赖于该加载。我们将这种类型的依赖称为地址依赖 (address dependency)。回到图 6 (c) 所示的例子，我们只是保守地认为存储 “store &y, r2” 依赖于加载 “r1 = load &x”，即使编译器知道 r1 永远不会指向 z 的地址。因此，在我们的实现中，如果编译器希望将某个存储 \( {s}^{\prime } \)（本例中的 “store &y, r2”）重排序到另一个存储 \( s \)（本例中的 “store r1,0 ”）之前，那么它必须使 \( {s}^{\prime } \) 依赖于 \( s \) 的地址所依赖的所有加载（本例中的 “r1 = load &x”）。

    Consider the example shown in Figure 6 (d), in which we need to answer the same question of whether the last store "store &y, r2" depends on the first load "r1 = load &x". Similar to the example shown in Figure 6 (c), the store "store &y, r2" does not have a data dependency or explicit control dependency on "r1 = load &x"; however, given z=1 initially, the value that the memory location y will hold can actually be value 1 or 0 , depending on whether the condition "r1 != 0" is true. The essential reason why we have such dependency is that in an untaken branch there exists a store (i.e., "store & z, 0" in the else branch) which overwrites a memory location that is later read. Similar to address dependency, a fine-grained definition of this type of dependency would require the introduction of a program analysis and complicate our dependence notion. Instead, we take a conservative approach by stating that if the condition of a control flow block (i.e., an if/else block or while loop) depends on a load, and the untaken branch has a syntactically reachable store, then all subsequent stores after the conditional branch also depend on that load. We refer to this type of dependency as implicit control dependency.

    考虑图 6 (d) 所示的示例，其中我们需要回答同一个问题：最后一个存储“store &y, r2”是否依赖于第一个加载“r1 = load &x”。与图 6 (c) 所示的示例类似，存储“store &y, r2”对“r1 = load &x”不存在数据依赖 (data dependency) 或显式控制依赖 (explicit control dependency)；然而，给定初始时 z=1，内存位置 y 实际持有的值可以是 1 或 0，这取决于条件“r1 != 0”是否为真。之所以会存在这样的依赖，其根本原因在于：在未被采用的分支 (untaken branch) 中，存在一个存储（即 else 分支中的“store & z, 0”），它会覆盖一个随后被读取的内存位置。与地址依赖 (address dependency) 类似，对这种依赖类型进行细粒度定义将需要引入程序分析 (program analysis)，并使我们的依赖概念复杂化。因此，我们采取一种保守方法，即规定：如果一个控制流块 (control flow block)（即 if/else 块或 while 循环）的条件依赖于某个加载，并且未被采用的分支具有一个语法上可达的存储 (syntactically reachable store)，那么条件分支之后的所有后续存储也都依赖于该加载。我们将这种依赖类型称为隐式控制依赖 (implicit control dependency)。

    We can see that the address dependency set and implicit control dependency set share two commonalities: (1) along with the execution of a program, both dependency sets will only be augmented by adding more loads; and (2) whenever a future store statement is executed, we must ensure that the future store depends on the loads in these two sets. Hence, our operational semantics uses \( {FD} \) to record the union of address dependency and implicit control dependency, on which all future stores depend.

    我们可以看到，地址依赖集 (address dependency set) 和隐式控制依赖集 (implicit control dependency set) 具有两个共同点：(1) 随着程序的执行，这两个依赖集都只会通过添加更多的加载 (loads) 而得到扩充；以及 (2) 每当未来的存储语句 (store statement) 被执行时，我们都必须确保该未来的存储依赖于这两个集合中的加载。因此，我们的操作语义 (operational semantics) 使用 \( {FD} \) 来记录地址依赖和隐式控制依赖的并集，而所有未来的存储都依赖于它。

    (4) Phi \( \left( \phi \right) \) functions: A phi function "v= \( \phi \left( {{\mathrm{v}}_{0},{\mathrm{v}}_{1}}\right) \) " with respect to condition cond is essentially an assignment statement that selects its right-hand side value associated with cond, whether cond is from an if/else branch or a while loop. For an if/else branch, \( {v}_{0} \) comes from the if branch, and \( {v}_{1} \) comes from the else branch. For a while loop, \( {v}_{0} \) comes from outside the loop, and \( {v}_{1} \) comes from inside the loop. For example, if the phi function is associated with an if/else branch, and condition cond is true, then the phi function effectively becomes "v=v0" with an extra (explicit) control dependency on cond. Thus, the phi variable v depends on whatever loads \( {\mathrm{v}}_{0} \) and cond depend on. In our rules, the assign_phi function transform phi functions to assignments so that we can apply the Assignment rule for data dependency, and the taint_phi function and the Phi.Taint rule together taint the phi variables with the explicit control dependency on the condition. For example, the phi variable r5 in line 9 in Figure 5 has an explicit control dependency on the if condition, which depends on the load "r1 = load &x". As a result, by the Store rule, the store "store &z, r5" in line 10 also depends the "r1 = load &x".

    (4) Phi \( \left( \phi \right) \) 函数 (functions)：关于条件 cond 的 phi 函数 “v= \( \phi \left( {{\mathrm{v}}_{0},{\mathrm{v}}_{1}}\right) \) ” 本质上是一个赋值语句，它根据 cond 选择其右侧对应的值，无论 cond 来自 if/else 分支还是 while 循环。对于 if/else 分支，\( {v}_{0} \) 来自 if 分支，而 \( {v}_{1} \) 来自 else 分支。对于 while 循环，\( {v}_{0} \) 来自循环外部，而 \( {v}_{1} \) 来自循环内部。例如，如果 phi 函数与一个 if/else 分支相关联，并且条件 cond 为真，那么 phi 函数实际上变为 “v=v0”，并额外具有对 cond 的（显式）控制依赖 (control dependency)。因此，phi 变量 v 依赖于加载 \( {\mathrm{v}}_{0} \) 所依赖的任何内容以及 cond 所依赖的任何内容。在我们的规则中，assign_phi 函数将 phi 函数转换为赋值语句，以便我们能够应用用于数据依赖的赋值规则 (Assignment rule)，而 taint_phi 函数和 Phi.Taint 规则 (rule) 一起通过条件上的显式控制依赖来污染 phi 变量。例如，图 5 第 9 行中的 phi 变量 r5 对 if 条件具有显式控制依赖，而该条件又依赖于加载 “r1 = load &x”。因此，根据存储规则 (Store rule)，第 10 行中的存储 “store &z, r5” 也依赖于 “r1 = load &x”。

    (5) If/else branches: An if/else branch can potentially introduce explicit and implicit control dependencies, as shown in Figure 6 (b) and (d). In addition, we must ensure that the phi variables associated with the branch also have dependencies on the appropriate right-hand side variable and a dependency on the if condition as discussed above. The If.True and If.False rules are applied when the if condition is true or false, respectively. The hasReachableStore() function returns true or false for whether or not a given block of statements has a syntactically reachable store (i.e., potential store). Note that the explicit control dependency set \( {PC} \) returns to its original state after we execute the if/else branch, and we track implicit control dependencies by applying the hasReachableStore() function on the untaken branch.

    (5) if/else 分支 (branch)：if/else 分支 (branch) 可能会引入显式控制依赖 (control dependencies) 和隐式控制依赖 (control dependencies)，如图 6(b) 和 (d) 所示。此外，我们必须确保与该分支相关联的 phi 变量 (variables) 也对适当的右侧变量具有依赖关系，并且如上所述，对 if 条件具有依赖关系。当 if 条件为真或为假时，分别应用 If.True 和 If.False 规则。hasReachableStore() 函数在给定语句块是否具有语法上可达的 store（即，潜在的 store）这一点上返回 true 或 false。注意，在我们执行完 if/else 分支 (branch) 之后，显式控制依赖集 \( {PC} \) 会恢复到其原始状态，而我们通过在未选择的分支上应用 hasReachableStore() 函数来跟踪隐式控制依赖。

    (6) While loops: In our dependency rules, a while loop can be unrolled indefinitely and viewed as if they were nested if/else branches. However, in terms of formalization, unlike normal if/else branches, we need to distinguish the first time we enter the while loop from later loop continuations for two reasons: (1) we need to assign the phi functions differently depending on whether we enter the loop for the first time or not; and (2) when we finish executing a loop, since we need to recover the explicit control dependency set \( {PC} \) , we need to record the old \( {PC} \) set based on the two different cases. Thus, we define the While.Taken rule for cases where we enter the loop for the first time and the loop condition is true, and the While.Untaken rule for those where we enter the loop for the first time and the loop condition is false. Note that once a while loop is taken for the first time, we change the loop keyword from while to loop as an indicator that the loop has been taken at least once. Also, when a while loop is taken for the first time, we record the old \( {PC} \) so that we can recover the \( {PC} \) status when we finish executing the loop. We then define the Loop.Taken rule for cases where a loop is taken after the first time, and the Loop.Untaken rule for cases where a loop is finished after being executed at least once. Note that applying any of these four rules has an effect on the explicit control dependency set \( {PC} \) and future store dependency \( {FD} \) similar to that of the conditional branch rules.

    （6）while 循环：在我们的依赖规则中，while 循环可以被无限展开，并被视为仿佛是嵌套的 if/else 分支。然而，就形式化 (formalization) 而言，不同于普通的 if/else 分支，我们需要区分第一次进入 while 循环和后续的循环继续，这有两个原因：(1) 我们需要根据是否是第一次进入循环，以不同方式赋值 phi 函数；以及 (2) 当我们完成一个循环的执行时，由于我们需要恢复显式控制依赖集 \( {PC} \)，我们需要基于这两种不同情况记录旧的 \( {PC} \) 集。因此，我们定义 While.Taken 规则，用于第一次进入循环且循环条件为真的情况；并定义 While.Untaken 规则，用于第一次进入循环且循环条件为假的情况。请注意，一旦 while 循环第一次被采用，我们就将循环关键字从 while 改为 loop，以此表明该循环至少已经被采用过一次。此外，当 while 循环第一次被采用时，我们会记录旧的 \( {PC} \)，以便在完成循环执行时恢复 \( {PC} \) 状态。随后，我们定义 Loop.Taken 规则，用于循环在第一次之后被采用的情况；并定义 Loop.Untaken 规则，用于循环在至少执行过一次之后结束的情况。请注意，应用这四条规则中的任何一条，都会对显式控制依赖集 \( {PC} \) 和未来存储依赖 (future store dependency) \( {FD} \) 产生与条件分支规则类似的影响。

    (7) Function calls: Since we only have function calls in which the functions are pre-defined and have a definite function name, a function call can be viewed as an inlined block of statements with extra data dependencies from the actual parameters to the formal parameters and from the return value to the actual function call result. Hence, to simplify the presentation and focus on the core problem, we omit the dependency rule involving function calls in the operational semantics shown above.

    （7）函数调用 (function calls)：由于我们只考虑函数 (functions) 预先定义且具有确定函数名的函数调用 (function call)，因此，函数调用 (function call) 可以被视为一个内联 (inlined) 的语句块 (block of statements)，并带有额外的数据依赖 (data dependencies)：从实际参数 (actual parameters) 到形式参数 (formal parameters)，以及从返回值 (return value) 到实际函数调用结果 (actual function call result)。因此，为了简化表述并聚焦于核心问题，我们在上文所示的操作语义 (operational semantics) 中省略了涉及函数调用 (function calls) 的依赖规则 (dependency rule)。

    However, this is not sufficient for real-world programming languages, which can have function pointers (e.g., C/C++) or virtual dispatch mechanisms (e.g., object-oriented programming languages). The essential problem is that when the address of a function call depends on some load \( l \) , we should conservatively assume that the function call could potentially have stores that write to any possible memory location and thus must ensure that any future store from the point of the function call also depends on load \( l \) . We refer to this type of dependency as a function dependency. It is important to note that the implementation of our dependency-preserving compiler shown in Section 3 effectively enforces function dependencies.

    然而，这对于现实世界的编程语言而言仍然不够，因为它们可能具有函数指针 (function pointers)（例如，C/C++）或虚分派机制 (virtual dispatch mechanisms)（例如，面向对象编程语言）。其根本问题在于：当函数调用的地址依赖于某个加载 \( l \) 时，我们应当保守地假设该函数调用可能具有会写入任何可能内存位置的存储，因此必须确保从该函数调用点开始的任何未来存储也依赖于加载 \( l \)。我们将这种类型的依赖称为函数依赖 (function dependency)。需要注意的是，第 3 节中展示的我们的依赖保持编译器 (dependency-preserving compiler) 的实现实际上有效地强制执行了函数依赖 (function dependencies)。

    2.3 A Load-Store-Order-Preserving Memory Model

    An alternative approach to eliminating out-of-thin-air behaviors is to strengthen the existing C/C++ memory model by requiring sequence-before \( \cup \) reads-from to be acyclic. This well-known C/C++ memory model variant has been proposed by researchers [Batty et al. 2013; Boehm and Demsky 2014; Vafeiadis and Narayan 2013] as one of the possible approaches to forbidding out-of-thin-air behaviors. Note that this is not the "perfect" fix to the problem since it forbids not just the problematic out-of-thin-air executions (e.g., Figure 2) but also some legitimate executions such as the load buffering example shown in Figure 1. This approach is less likely to be acceptable for Java-like memory models that must describe the behavior of all loads because it is likely to incur a much higher cost.

    一种替代性的消除凭空出现行为 (out-of-thin-air behaviors) 的方法，是通过要求顺序先于 (sequence-before) \( \cup \) 读取自 (reads-from) 为无环 (acyclic)，从而加强现有的 C/C++ 内存模型 (memory model)。这一广为人知的 C/C++ 内存模型 (memory model) 变体，已被研究人员 [Batty et al. 2013; Boehm and Demsky 2014; Vafeiadis and Narayan 2013] 提出，作为禁止凭空出现行为 (out-of-thin-air behaviors) 的可能方法之一。请注意，这并不是对该问题的“完美”修复，因为它不仅禁止了有问题的凭空出现执行 (out-of-thin-air executions)（例如，图 2），还禁止了一些合法执行，例如图 1 所示的加载缓冲 (load buffering) 示例。对于必须描述所有加载 (loads) 行为的类 Java 内存模型 (memory models) 而言，这种方法较不可能被接受，因为它很可能会带来高得多的成本。

    3 DEPENDENCY-PRESERVING COMPILER

    This section describes the design and implementation of our approach to preserving our extended memory model in the LLVM compiler infrastructure [Lattner and Adve 2004]. We target the LLVM compiler in this paper for two reasons: (1) LLVM is widely supported and considered by many as the state-of-the-art compiler framework; and (2) LLVM is not just adopted as a C/C++ compiler but is also adopted in the context of a commercial JVM, e.g., Azul's Falcon compiler [Azul 2017].

    本节描述了我们在 LLVM 编译器基础设施中保持我们扩展内存模型的方法的设计与实现 [Lattner and Adve 2004]。本文以 LLVM 编译器为目标，原因有二：(1) LLVM 得到了广泛支持，并被许多人认为是最先进的编译器框架；(2) LLVM 不仅被用作 C/C++ 编译器，而且还被应用于商业 JVM 的语境中，例如 Azul 的 Falcon 编译器 [Azul 2017]。

    The LLVM compiler infrastructure is designed to compile source code and generate optimized library or executable files in a modular and reusable fashion. The standard LLVM compilation pipeline is shown in Figure 7, and we illustrate the workflow as follows:

    LLVM 编译器基础设施 (compiler infrastructure) 旨在以模块化且可复用的方式编译源代码，并生成优化后的库文件或可执行文件。标准的 LLVM 编译流水线 (compilation pipeline) 如图 7 所示，我们将工作流程 (workflow) 说明如下：

    (3) The optimized LLVM IR generated in step 2 will then be passed to the LLVM backend code generator, which performs instruction selection, register allocation, peephole optimizations, etc., and finally generates optimized binary object files. In the LLVM tool chain, the LLVM static compiler - llc - implements this step. Note that the backend transformations are implemented as a list of code generation passes (LLVM machine passes performed in some machine code representations), and these passes can also potentially break dependencies. In general, the LLVM infrastructure supports multiple backend code generators for different architectures. In our work, we use the AArch64 (ARM's 64-bit architecture) backend as a case study and thus will focus on the code generation passes for AArch64 hardware. Our case study explore ARM 64 because it is the most relevant mainstream processor that implements a memory model that does not preserve load-store ordering. Intel processors implement the TSO memory model which by default preserves load-store ordering, and thus are expected to incur significantly less overhead to implement our memory model.

    （3）第 2 步中生成的优化后的 LLVM IR 随后将被传递给 LLVM 后端代码生成器 (backend code generator)，该生成器执行指令选择、寄存器分配、窥孔优化等，并最终生成优化后的二进制目标文件。在 LLVM 工具链中，LLVM 静态编译器 (static compiler) - llc - 实现了这一步。需要注意的是，后端变换 (backend transformations) 被实现为一系列代码生成遍 (code generation passes)（即在某些机器代码表示中执行的 LLVM 机器遍 (LLVM machine passes)），而这些遍也可能会破坏依赖关系。总体而言，LLVM 基础设施 (infrastructure) 支持面向不同架构的多个后端代码生成器 (backend code generators)。在我们的工作中，我们使用 AArch64（ARM 的 64 位架构）后端作为案例研究，因此将重点关注面向 AArch64 硬件的代码生成遍 (code generation passes)。我们的案例研究考察 ARM 64，因为它是最相关的主流处理器，并且实现了一种不保持加载-存储顺序的内存模型 (memory model)。Intel 处理器实现的是 TSO 内存模型 (memory model)，该模型默认保持加载-存储顺序，因此预计在实现我们的内存模型 (memory model) 时将产生显著更少的开销。

    (4) Finally, the system linker will link the optimized object files and generate optimized library or executable files. Note that on a Linux machine, it is a common case to use the GNU linker as the default system linker.

    （4）最后，系统链接器将链接经优化的目标文件，并生成经优化的库文件或可执行文件。请注意，在 Linux 机器上，使用 GNU 链接器 (linker) 作为默认系统链接器是一种常见情况。

    As shown in the above pipeline, in order to ensure that dependencies are preserved down to the generated binary code, we must make sure the transformations in step 2 and 3 preserve the dependencies. Ideally, we should review each transformation pass. If it can potentially break dependencies, we should modify the optimization to retain most of the benefits of the optimization while preserving dependencies; otherwise, we should leave the pass unchanged. However, for our research project, this incurs too much manual effort. There are more than 50 LLVM transformation passes in step 2. Fortunately, a preliminary result shows that if we run only a select set of 35 IR-to-IR passes alone in step 2, the performance loss over running the standard set of IR-to-IR passes (as called in "opt -O3") is only 1.8%. As a result, we disable all other IR-to-IR passes and focus our efforts on the select set of passes. We show the set of IR passes that we enable in the extended version of this paper [Ou and Demsky 2018].

    如上述流程所示，为了确保依赖关系一直被保留到生成的二进制代码，我们必须确保步骤 2 和 3 中的变换能够保留这些依赖关系。理想情况下，我们应该审查每一个变换遍。若其有可能破坏依赖关系，我们就应当修改该优化，在保留依赖关系的同时尽可能保留优化的大部分收益；否则，我们应当保持该遍不变。然而，对于我们的研究项目而言，这会带来过多的人工工作量。步骤 2 中有 50 多个 LLVM 变换遍。幸运的是，一个初步结果表明，如果我们在步骤 2 中仅运行一组精选的 35 个 IR 到 IR 遍，和运行标准的 IR 到 IR 遍集合（如 "opt -O3" 中所调用的那样）相比，性能损失仅为 1.8%。因此，我们禁用了所有其他 IR 到 IR 遍，并将精力集中在这组精选的遍上。我们在本文的扩展版本中展示了我们启用的 IR 遍集合 [Ou and Demsky 2018]。

    3.2 Implementation

    Several important compiler optimization passes are inherently dependency-preserving and require either no changes or only minor changes. We first discuss those that require no changes and then discuss how we modify/disable the remaining passes to preserve dependencies.

    若干重要的编译器优化传递 (compiler optimization passes) 本质上是保留依赖关系的 (dependency-preserving)，并且要么不需要任何修改，要么只需要少量修改。我们首先讨论那些不需要修改的传递，然后讨论我们如何修改/禁用其余传递，以保留依赖关系。

    3.2.1 Unmodified Passes.

    Function inlining: This optimization expands specific function call sites in the body of the caller functions, potentially reducing function call overhead and introducing more opportunities for later optimizations. Our preliminary result shows that turning off inlining incurs an overhead of 26% on AArch64 targets. Fortunately, no change is required for this pass as long as we conservatively preserve the syntactic dependencies in all functions. For example, Figure 8 shows a function foo that internally calls another function bar.     Dead code elimination: Dead code elimination in general eliminates the instructions that are unreachable or have no visible effects to the program, and does not break dependencies. In LLVM, this corresponds to adce (aggressive dead code elimination) and dce (dead code elimination).

    This shows that multiple dependency-preserving passes combined together can break dependencies. The fundamental problem that causes this is the poorly defined notion of dependency in the IR. In the example in Figure 12 (c), the later simplifycfg pass has no information about whether the empty conditional branch carries a dependency to later stores, thus eliminating it can potentially break a dependency, as shown in this case. Ideally, if the IR was augmented with extra dependency edges between statements, we could use that information to ensure that a specific transformation does not break existing dependency edges. In practice, to make our approach simpler to implement in the existing LLVM framework without requiring large changes to LLVM's IR, we adopt a coarse-grained extension to the IR such that basic blocks contain extra information indicating whether some other statements may or may not depend on them. In this case, when we construct the SSA form and encounter a PHI node that has the same value from multiple basic blocks, we conservatively mark the incoming blocks as unremovable to preserve such control flow blocks even if they are empty.

    这表明，将多个保持依赖关系 (dependency-preserving) 的遍历 (passes) 组合在一起时，可能会破坏依赖关系 (dependencies)。导致这一点的根本问题在于中间表示 (IR) 中依赖关系 (dependency) 这一概念定义不清。在图 12 (c) 的示例中，后续的 simplifycfg 遍历 (pass) 并不知道这个空的条件分支 (conditional branch) 是否携带了指向后续存储 (stores) 的依赖关系 (dependency)，因此消除它可能会破坏依赖关系 (dependency)，正如本例所示。理想情况下，如果中间表示 (IR) 通过在语句 (statements) 之间增加额外的依赖边 (dependency edges) 得到增强，我们就可以利用这些信息来确保特定的变换 (transformation) 不会破坏现有的依赖边 (dependency edges)。在实践中，为了使我们的方法更容易在现有的 LLVM 框架 (framework) 中实现，而不需要对 LLVM 的中间表示 (IR) 进行大规模修改，我们对中间表示 (IR) 采用一种粗粒度 (coarse-grained) 扩展 (extension)，使得基本块 (basic blocks) 包含额外信息，以指示其他某些语句 (statements) 是否可能依赖于它们。在这种情况下，当我们构造静态单赋值形式 (SSA form) 并遇到一个来自多个基本块 (basic blocks) 且具有相同值的 PHI 节点 (PHI node) 时，我们会保守地将这些输入块 (incoming blocks) 标记为不可移除 (unremovable)，以保留此类控制流块 (control flow blocks)，即使它们是空的。

    Passes that potentially reorder stores: According to our dependency notion, reordering an earlier store \( {s}_{1} \) and a later store \( {s}_{2} \) can potentially break address dependencies if the address of \( {s}_{1} \) depends on some load that \( {s}_{2} \) does not depend on.     可能重排存储 (store) 的优化过程 (passes)：根据我们的依赖性 (dependency) 概念，将较早的存储 (store) \( {s}_{1} \) 与较晚的存储 (store) \( {s}_{2} \) 重排，可能会破坏地址依赖性 (address dependencies)，如果 \( {s}_{1} \) 的地址依赖于某个加载 (load)，而 \( {s}_{2} \) 不依赖于该加载。我们将可能重排存储 (store) 的优化过程 (passes) 及我们相应的策略列举如下：

    4 LOAD-STORE-ORDER-PRESERVING COMPILER

    This section describes the implementation of our approach to preserving atomic load-store ordering in the LLVM compiler for AArch64 targets. In LLVM IR, atomic load/store operations are special load/store operations with memory ordering parameters similar to their C/C++ counterparts (e.g., memory_order_acquire), and atomic read-modify-write operations (e.g., compare_exchange_strong and fetch_add) are represented as atomic rmw or cmpxchg. Similar to the dependency-preserving approach, we need to ensure that both IR-level optimizations and the backend generate code that preserves load-store ordering for atomic operations.

    本节描述了我们在面向 AArch64 目标的 LLVM 编译器中实现保持原子 (atomic) 加载-存储排序的方法。在 LLVM IR 中，原子 (atomic) 加载/存储操作是具有内存排序参数的特殊加载/存储操作，这些参数与其 C/C++ 对应项类似（例如，memory_order_acquire）；而原子 (atomic) 读-修改-写操作（例如，compare_exchange_strong 和 fetch_add）则表示为 atomic rmw 或 cmpxchg。与保持依赖关系的方法类似，我们需要确保 IR 级优化和后端都能生成保持原子 (atomic) 操作的加载-存储排序的代码。

    4.1 Target-Independent Optimizations

    For IR optimization passes, we only need to focus on those passes that can potentially perform load-store reordering to atomic load/store operations, which fortunately is a small subset of the IR optimization passes. For example, these passes include the loop invariant code motion pass (licm), the memory copy optimization pass (memcpyopt), the dead store elimination pass (dse), the SLP vectorization pass, etc. We carefully reviewed these passes and found that they do not perform load-store reordering for atomic operations by design. The reasons include: (1) the semantics of atomic operations disallow the optimization (e.g., atomic operations cannot be optimized into a memcpy/memset operation since it can potentially reorder the atomic operations and change the visible side effect) or (2) it is tricky to reason about the correctness of optimizations of atomic operations, and the optimization is not especially important in most cases. For example, the licm pass will optimize normal loads/store out of a loop but is conservative with atomic operations. As a result, we can enable all the original IR-level passes.

    对于 IR 优化 (optimization) 过程 (passes)，我们只需要关注那些可能对原子加载/存储操作执行加载-存储重排序的过程 (passes)，幸运的是，这只是 IR 优化过程 (passes) 的一个很小子集。例如，这些过程 (passes) 包括循环不变代码外提过程 (loop invariant code motion pass, licm)、内存拷贝优化过程 (memory copy optimization pass, memcpyopt)、死存储消除过程 (dead store elimination pass, dse)、SLP 向量化过程 (SLP vectorization pass) 等。我们仔细审查了这些过程 (passes)，发现按照设计，它们不会对原子操作执行加载-存储重排序。原因包括：(1) 原子操作的语义 (semantics) 不允许这种优化（例如，原子操作不能被优化为 memcpy/memset 操作，因为这可能会重排序原子操作并改变可见副作用）；或 (2) 对原子操作的优化正确性进行推理很棘手，而且在大多数情况下，这种优化并不是特别重要。例如，licm 过程 (pass) 会将普通加载/存储优化到循环外，但对原子操作采取保守策略。因此，我们可以启用所有原始的 IR 级别过程 (passes)。

    4.2 Backend Optimizations for AArch64

    4.2.1 LLVM AArch64 Backend for C/C++ Atomics. Figure 15 shows how the LLVM backend compiles C++ atomics to assembly for AArch64 targets. In example (a), an atomic load/store with memory_order_relaxed ordering parameter is compiled to a normal load/store instruction, while an atomic load with memory_order_acquire \( {}^{5} \) or store with memory_order_release is compiled to a load-acquire (1dar) or store-release (stlr), respectively, which are load and store instructions in AArch64 with implicit one-way barrier semantics. For example, the normal load and store in line 2 and 3 can be reordered by the processor at runtime, while the ldar in line 1 guarantees that loads/stores after it cannot be reordered before the load. Similarly, all loads/stores before the stlr in line 5 cannot be reordered after it. In example (b), a fetch_add operation is compiled to a loop that continuously attempts to atomically fetch and add one to the memory location. It takes advantage of the exclusive load/store (1dxr/stxr) pair, which has exclusive locking semantics on the load/store address to guarantee the read-modify-write is atomic. It is important to note that in the ARMv8 architecture, the success bit (w10 in this example) of a successful store-exclusive is not supposed to introduce any dependency from the load-exclusive it is paired with [Pulte et al. 2018]. As a result, the store in line 6 does not have a dependency on the load in line 2 and thus can be reordered before it. In example (c), a compare-and-swap operation is compiled to a conditional branch that compares the load value with the expected value and then decides whether or not it should store the new value to the memory. Since there is a control dependency (line 3) from the load part (line 2) to any stores after the compare-and-swap operation, those subsequent stores cannot be reordered before the load part. The conclusions from these three examples are (1) that atomic loads that have a stronger ordering parameter than memory_order_relaxed and atomic compare-and-swap operations already have an ordering constraint relative to subsequent stores, and (2) that we only need to preserve the ordering from the relaxed load and those fetch_add-like read-modify-write operations (with ordering parameters that do not have acquire semantics) to subsequent stores.

    4.2.2 Forbidding Reordering of Loads and Stores in AArch64. For cases in which a load is followed by a store, one could alternatively add a bogus address dependency [Maranget et al. 2012] from the load to the store to guarantee the ordering. Also, a similar strategy with respect to adding address dependency to insert (between the target relaxed load and subsequent stores) a bogus load whose address depends on the target relaxed load.     5 EVALUATION

    In this section, we evaluate the cost of the two approaches to avoiding out-of-thin-air behaviors in C/C++ for AArch64 targets. In our evaluation, we report execution times on a Firefly-RK3399 board, which has a six-core 64-bit CPU (two ARM Cortex-A72 cores and four ARM Cortex-A53 cores), 4 GB memory, and runs Ubuntu 16.04.2. We have made both our compiler implementations and benchmarks publicly available at http://plrg.eecs.uci.edu/oota-html.As Sullivan [2017] shows, the performance results can vary depending on the processor in question. More specifically, their results seem to suggest that dependencies and fences may exhibit less performance penalty in ARMv8 than in ARMv7 and Power architectures. Ideally, the evaluation would have been more complete if we also considered the ARMv7 and Power architectures; however, in LLVM, they use different backends (which does require review and modifications) to generate architecture-specific code, so this is a non-trivial effort. As a first-step, we believe that evaluating the approaches on a relatively new version of 64-bit ARM processor could still be a useful indicator for future processors, and decided to leave the evaluation on the ARMv7 and Power architectures as future work.

    在本节中，我们评估了针对 AArch64 目标，在 C/C++ 中避免无中生有 (out-of-thin-air) 行为的两种方法的成本。在我们的评估中，我们报告了在 Firefly-RK3399 开发板上的执行时间，该开发板配备了一个六核 64 位 CPU（两个 ARM Cortex-A72 核心和四个 ARM Cortex-A53 核心）、4 GB 内存，并运行 Ubuntu 16.04.2。我们已将编译器 (compiler) 的两种实现以及基准测试 (benchmarks) 公开发布于 http://plrg.eecs.uci.edu/oota-html。正如 Sullivan [2017] 所示，性能结果可能会因所讨论的处理器 (processor) 而异。更具体地说，他们的结果似乎表明，在 ARMv8 中，依赖 (dependencies) 和栅栏 (fences) 所带来的性能损失可能小于在 ARMv7 和 Power 架构中的情况。理想情况下，如果我们也考虑 ARMv7 和 Power 架构，那么这项评估本可以更加完整；然而，在 LLVM 中，它们使用不同的后端 (backends)（这确实需要审查和修改）来生成架构特定代码 (architecture-specific code)，因此这并非一项轻而易举的工作。作为第一步，我们认为，在相对较新的 64 位 ARM 处理器版本上评估这些方法，仍然可以作为未来处理器的一个有用指标，因此决定将对 ARMv7 和 Power 架构的评估留作未来工作。

    5.1 Cost of Preserving Dependencies

    Although avoiding out-of-thin-air behaviors applies only to multi-threaded code, our dependency-preserving approach incurs overhead for both single-threaded and multi-threaded programs. Single-threaded code represents a worse case scenario-the memory system bandwidth is not utilized by other cores and thus the extra instructions we add have a relatively higher cost. Thus, we measure the overheads of our dependency-preserving optimizations on single-threaded code.

    尽管避免凭空产生 (out-of-thin-air) 行为只适用于多线程代码，但我们保持依赖关系 (dependency-preserving) 的方法会给单线程和多线程程序都带来开销。单线程代码代表了一种更糟糕的情况——内存系统带宽没有被其他核心利用，因此我们添加的额外指令具有相对更高的成本。因此，我们在单线程代码上测量了我们保持依赖关系 (dependency-preserving) 优化所带来的开销。

Due to the amount of engineering work needed to review/modify each optimization pass, we only select a core set of IR-level optimization passes (35 out of 46) to carefully review and modify when necessary to implement the dependency-preserving compiler. The configuration "Partial Optimization" is the stock LLVM compiler whose IR-level optimizations only include the same core set of passes that are enabled in our dependency-preserving compiler.

    5.2 Cost of Forbidding Load-Store Reordering

    Unlike the dependency-preserving approach, forbidding load-store reordering to avoid out-of-thin-air behaviors only affects relaxed atomics in C/C++11. Hence, for example, the load-store-order-preserving approach should impose no overhead on the SPEC CPU2006 benchmarks because they do not use any C/C++ relaxed atomics. We believe that relaxed atomics will primarily appear in concurrent data structure code, while most other program code would not be affected since they would likely use other primitives that provide stronger semantics, e.g., locks and atomics with memory_order_seq_cst. Hence, we focus on evaluating the performance overhead incurred by forbidding load-store reordering for real-world concurrent data structures. The results can be roughly viewed as the upper bound of the performance overhead of this approach. The performance impact on full applications would depend on how much time those applications spend in concurrent data structure code. Ideally, we would also like to benchmark full applications; however, many existing multi-threaded applications that we have access to are not kept up-to-date with the C/C++ memory model, and porting them to use C/C++ atomics is a non-trivial effort. Hence we leave it as future work.

    与保持依赖关系 (dependency-preserving) 的方法不同，为了避免凭空产生 (out-of-thin-air) 行为而禁止加载-存储重排序 (load-store reordering)，只会影响 C/C++11 中的宽松原子操作 (relaxed atomics)。因此，例如，保持加载-存储顺序 (load-store-order-preserving) 的方法不应给 SPEC CPU2006 基准测试带来任何开销，因为它们不使用任何 C/C++ 宽松原子操作 (relaxed atomics)。我们认为，宽松原子操作 (relaxed atomics) 将主要出现在并发数据结构 (concurrent data structure) 代码中，而大多数其他程序代码不会受到影响，因为它们很可能会使用提供更强语义的其他原语，例如锁和具有 memory_order_seq_cst 的原子操作。因此，我们重点评估在真实世界并发数据结构 (concurrent data structures) 中，禁止加载-存储重排序 (load-store reordering) 所带来的性能开销。其结果可以被粗略地视为这种方法性能开销的上界。对完整应用程序的性能影响将取决于这些应用程序在并发数据结构 (concurrent data structure) 代码中花费了多少时间。理想情况下，我们也希望对完整应用程序进行基准测试；然而，我们能够获得的许多现有多线程应用程序并未持续更新以适配 C/C++ 内存模型 (memory model)，而将它们移植为使用 C/C++ 原子操作 (atomics) 需要付出非平凡的努力。因此，我们将其留待未来工作。

    5.2.1 Concurrent Data Structures with Multiple Threads. In this evaluation, we gather a total set of 43 real-world concurrent data structures from several different sources, which range from basic synchronization primitive implementations, concurrent queues/stacks/deques to concurrent maps. Most of these data structures are lock-free, and all of them intensively utilize C/C++11 atomics. In more details, among these concurrent data structures, we collect 18 of them from the CDS C++ library [Khiszinsky 2017], 13 of them from the Folly library [Facebook 2018], 4 different implementations of concurrent maps from the Junction library [Preshing 2018], 2 queue implementations by Rigtorp [2017a, b], and 6 benchmarks used in CDSSPEC [Ou and Demsky 2017].

    5.2.1 使用多线程的并发数据结构 (Concurrent Data Structures)。在这项评估中，我们从多个不同来源收集了总计 43 个真实世界的并发数据结构 (concurrent data structures)，其范围涵盖基础同步原语 (synchronization primitive) 实现、并发队列/栈/双端队列到并发映射 (map)。这些数据结构中的大多数都是无锁的 (lock-free)，并且它们全部都密集使用 C/C++11 原子操作 (atomics)。更详细地说，在这些并发数据结构中，我们从 CDS C++ 库 (library) [Khiszinsky 2017] 中收集了其中 18 个，从 Folly 库 (library) [Facebook 2018] 中收集了其中 13 个，从 Junction 库 (library) [Preshing 2018] 中收集了 4 种不同的并发映射 (map) 实现，由 Rigtorp [2017a, b] 提供的 2 种队列实现，以及 CDSSPEC [Ou and Demsky 2017] 中使用的 6 个基准测试 (benchmarks)。

    We ran each benchmark using 7 compiler configurations: (1) the stock LLVM compiler with all optimizations enabled (-03), i.e., Full Optimization; (2) our load-store-order-preserving compiler which adds bogus conditional branches after relaxed loads (Bogus Conditional Branch); (3) a variant of configuration 2 which adds address dependencies to existing stores rather than bogus conditional branches if there is a subsequent store after a relaxed load (Address Dependency to Store); (4) a modified compiler which adds address dependencies from relaxed loads to a subsequent load, which can be an existing load if any or an intentionally inserted bogus load otherwise (Bogus Load). Note that for a target relaxed load, we insert a bogus load whose address is the same as the relaxed load to avoid cache misses; (5) a modified compiler which treats relaxed loads as acquire loads (Acquire Load); (6) a modified compiler which treats relaxed stores as release stores (Release Store); and (7) a modified compiler which inserts "dmb 1d" fences before relaxed stores (DMB Fence).

    我们使用 7 种编译器配置运行了每个基准测试： (1) 启用所有优化（-03）的原版 LLVM 编译器，即完全优化 (Full Optimization)；(2) 我们保持加载-存储顺序 (load-store-order-preserving) 的编译器，它在宽松加载 (relaxed loads) 之后添加伪条件分支 (bogus conditional branches)（伪条件分支 (Bogus Conditional Branch)）；(3) 配置 2 的一个变体，如果在宽松加载 (relaxed load) 之后存在后续存储 (store)，则向现有存储添加地址依赖 (address dependencies)，而不是添加伪条件分支 (bogus conditional branches)（到存储的地址依赖 (Address Dependency to Store)）；(4) 一个修改后的编译器，它从宽松加载 (relaxed loads) 向后续加载 (load) 添加地址依赖 (address dependencies)；如果存在现有加载，则可以使用该现有加载，否则插入一个有意添加的伪加载 (bogus load)（伪加载 (Bogus Load)）。请注意，对于目标宽松加载 (target relaxed load)，我们插入一个伪加载 (bogus load)，其地址与该宽松加载相同，以避免缓存未命中；(5) 一个修改后的编译器，它将宽松加载 (relaxed loads) 视为获取加载 (acquire loads)（获取加载 (Acquire Load)）；(6) 一个修改后的编译器，它将宽松存储 (relaxed stores) 视为释放存储 (release stores)（释放存储 (Release Store)）；以及 (7) 一个修改后的编译器，它在宽松存储 (relaxed stores) 之前插入 “dmb 1d” 栅栏 (fences)（DMB 栅栏 (DMB Fence)）。

    Since the Firefly-RK3399 board has two faster ARM Cortex-A72 cores and four slower ARM Cortex-A53 cores, it can potentially increase the noise in our performance evaluation if we run the benchmarks with multiple threads across the two different types of cores. Hence, we ran each of our benchmark with two threads, and each thread exclusively runs on a Cortex-A72 core. We ran each benchmark test case for 5 times and use the average (arithmetic mean) of those 5 runs as the execution time for each benchmark test case. For a benchmark in which there exist multiple variants, we use the geometric mean of the execution time of all the variants as the execution time of that benchmark. Although we ran the benchmarks with only two threads in this experiment, it is important to note that the extra overhead (i.e., extra dependencies or fences) that we introduce in this approach is local to each core and thus should not result in extra communication between cores, and hence one would not expect scaling issues; moreover, if the processor has limited memory bandwidth, as the number of cores utilized increases, the relative overhead of these extra dependencies or fences should become smaller.

    由于 Firefly-RK3399 开发板具有两个更快的 ARM Cortex-A72 核心和四个较慢的 ARM Cortex-A53 核心，如果我们让基准测试 (benchmark) 使用多个线程跨这两种不同类型的核心运行，则可能会增加我们在性能评估 (performance evaluation) 中的噪声 (noise)。因此，我们让每个基准测试 (benchmark) 都使用两个线程运行，并且每个线程都仅在一个 Cortex-A72 核心上运行。我们将每个基准测试用例 (benchmark test case) 运行 5 次，并使用这 5 次运行的平均值（算术平均数）作为每个基准测试用例的执行时间。对于存在多个变体 (variant) 的基准测试 (benchmark)，我们使用所有变体执行时间的几何平均数作为该基准测试 (benchmark) 的执行时间。尽管我们在本实验中仅使用两个线程运行这些基准测试 (benchmark)，但需要注意的是，我们在这种方法中引入的额外开销（即，额外的依赖关系 (dependencies) 或栅栏 (fences)）对于每个核心而言都是局部的，因此不应导致核心之间的额外通信，所以理论上不应出现可扩展性 (scaling) 问题；此外，如果处理器具有有限的内存带宽 (memory bandwidth)，那么随着所使用核心数量的增加，这些额外依赖关系 (dependencies) 或栅栏 (fences) 的相对开销应会变得更小。

    6 RELATED WORK

    In spite of much research on high-performance concurrent programming languages, we still do not have a definitive solution to the out-of-thin-air problem.

    尽管已经有大量关于高性能并发编程语言 (concurrent programming languages) 的研究，我们仍然没有针对凭空出现问题 (out-of-thin-air problem) 的最终解决方案。

    The C/C++11 memory model [Batty et al. 2011; Becker 2011; Boehm and Adve 2008; JTC 2011] does not forbid out-of-thin-air executions; and the C++14 memory model [JTC 2014] does not clearly define out-of-thin-air behaviors and only vaguely states that implementations should ensure that out-of-thin-air values that circularly depend on their computations should be disallowed. In our dependency-preserving approach, we formally define a notion of dependency and evaluate a prototype implementation on widely deployed commercial hardware.

    C/C++11 内存模型 (memory model) [Batty et al. 2011; Becker 2011; Boehm and Adve 2008; JTC 2011] 并不禁止无中生有执行 (out-of-thin-air executions)；而 C++14 内存模型 (memory model) [JTC 2014] 也未明确定义无中生有行为 (out-of-thin-air behaviors)，只是含糊地指出，实现应确保那些以循环方式依赖于其计算的无中生有值 (out-of-thin-air values) 应被禁止。在我们保持依赖关系的方法 (dependency-preserving approach) 中，我们形式化地定义了依赖关系 (dependency) 这一概念，并在广泛部署的商用硬件上评估了一个原型实现 (prototype implementation)。

    Boehm and Demsky [2014] propose the approach of ensuring that \( {sb} \cup {rf} \) is acyclic for relaxed atomics, but the actual overhead was unclear. Our work complements this by providing an initial evaluation on the overhead of the approach for execution of real-world concurrent data structure code on a mainstream processor.

    Boehm 和 Demsky [2014] 提出了一种方法，即确保对于宽松原子操作 (relaxed atomics)，\( {sb} \cup {rf} \) 是无环的，但其实际开销尚不明确。我们的工作对这一点进行了补充，提供了该方法在主流处理器上执行真实世界并发数据结构代码时开销的初步评估。

    The Java memory model [Manson et al. 2005; Shipilëv 2016a, b] disallows the canonical out-of-thin-air example shown in Figure 2 by establishing a notion of causality and showing that there cannot exist a justifying execution for r1=r2=42. However, the Java memory model was later found unsound with respect to some common compiler optimizations [Cenciarelli et al. 2007; Ševčík and Aspinall 2008] such as redundant read elimination. The fact that our dependency-preserving approach supports normal memory accesses rather than just C/C++ atomics indicates that it is a promising direction to explore for the Java memory model.

    Java 内存模型 (memory model) [Manson et al. 2005; Shipilëv 2016a, b] 通过建立因果关系 (causality) 的概念，并证明对于 r1=r2=42 不可能存在一个证明执行 (justifying execution)，从而禁止了图 2 中所示的经典无中生有 (out-of-thin-air) 示例。然而，后来人们发现，Java 内存模型 (memory model) 相对于一些常见的编译器优化 (compiler optimizations) [Cenciarelli et al. 2007; Ševčík and Aspinall 2008]（例如冗余读取消除 (redundant read elimination)）是不健全的 (unsound)。我们的依赖保持 (dependency-preserving) 方法支持普通内存访问 (normal memory accesses)，而不仅仅是 C/C++ 原子操作 (atomics)，这一事实表明，对于 Java 内存模型 (memory model) 而言，这是一个很有前景的探索方向。

    Dolan et al. [2018] have recently proposed a memory model that provides a property called local data race freedom, which guarantees that all data-race-free portions of a program still have sequential consistency semantics. They show that to implement their memory model, one would need to preserve the ordering between loads and stores. They implement it on OCaml with similar strategies that we use in our load-store-order-preserving compiler and show that the average overhead over stock OCaml compiler for ARMv8 architecture with sequential programs is ~0.6%. Although both their results and ours suggest that the overhead of preserving load-store ordering is relatively low on ARMv8 architecture, it is important to note the differences: (1) the primary goal of their model is to provide the local DRF property but not to prohibit OOTA behavior, although their model effectively disallows OOTA behavior; and (2) their results are based on OCaml, which has a Java-like memory model, and thus they need to preserve load-store ordering for all normal (non-atomic) accesses; while our approach targets the C/C++ memory model, which only affects the C/C++ atomics.

    Dolan 等人 [2018] 最近提出了一种内存模型 (memory model)，该模型提供了一种称为局部数据竞争自由 (local data race freedom) 的性质，保证程序中所有无数据竞争 (data-race-free) 的部分仍然具有顺序一致性 (sequential consistency) 语义。他们表明，为了实现其内存模型 (memory model)，需要保持加载 (loads) 与存储 (stores) 之间的顺序。他们在 OCaml 上采用了与我们在保持加载-存储顺序 (load-store-order-preserving) 编译器中使用的类似策略来实现该模型，并表明对于 ARMv8 架构上的顺序程序 (sequential programs)，相对于原生 OCaml 编译器 (stock OCaml compiler) 的平均开销约为 ~0.6%。尽管他们的结果和我们的结果都表明，在 ARMv8 架构上保持加载-存储顺序 (load-store ordering) 的开销相对较低，但需要注意以下差异：(1) 他们模型的主要目标是提供局部 DRF 性质，而不是禁止 OOTA 行为，尽管他们的模型实际上不允许 OOTA 行为；以及 (2) 他们的结果基于 OCaml，后者具有类似 Java 的内存模型 (memory model)，因此他们需要为所有普通（非原子）访问保持加载-存储顺序 (load-store ordering)；而我们的方法以 C/C++ 内存模型 (memory model) 为目标，因此只影响 C/C++ 原子操作 (atomics)。

    Sullivan [2017] has proposed an approach called Relaxed Memory Calculus (RMC) that is fundamentally different from the C/C++ and Java memory models. In the RMC approach, programmers essentially reason about the relative ordering of memory accesses in concurrent programs (in a fashion close to hardware memory models) and explicitly specify the constraints on the execution order and visibility of writes. Unfortunately, the RMC approach also suffers from OOTA behavior and needs further fixes. It is important to note that Sullivan [2017] demonstrates that ARMv8 seems to have a smaller overhead on dependencies/fences than ARMv7 and Power; more notably, SC atomics perform nearly as well as C11 atomics on ARMv8. Hence, this encourages future work to extend our evaluation to ARMv7 and Power architecture.

    Sullivan [2017] 提出了一种称为宽松内存演算 (Relaxed Memory Calculus, RMC) 的方法，这种方法与 C/C++ 和 Java 内存模型从根本上不同。在 RMC 方法中，程序员本质上是对并发程序中内存访问的相对顺序进行推理（其方式接近硬件内存模型），并显式指定对写入的执行顺序和可见性的约束。遗憾的是，RMC 方法也受到 OOTA 行为的影响，并且需要进一步修正。需要特别指出的是，Sullivan [2017] 表明，相较于 ARMv7 和 Power，ARMv8 在依赖/栅栏 (fences) 方面的开销似乎更小；更值得注意的是，在 ARMv8 上，SC 原子操作 (atomics) 的性能几乎与 C11 原子操作 (atomics) 一样好。因此，这鼓励未来的工作将我们的评估扩展到 ARMv7 和 Power 架构。

    Researchers have also proposed memory models whose goal is to disallow out-of-thin-air behaviors while embracing compiler optimizations. Jeffrey and Riely [2016]; Pichon-Pharabod and Sewell [2016] have proposed weak memory models based on event structures, which are sets of memory access events with some causal order and conflict relationship. Instead of focusing on a candidate execution, these approaches capture how different candidate executions relate to each other and diverge. Kang et al. [2017] propose a memory model that forbids out-of-thin-air behaviors based on operational semantics with timestamps and promises. Their approach introduces special reduction steps to allow a thread to perform a write with a promise that can be locally certified. Jagadeesan et al. [2010] propose an operational memory model for Java based on a notion of speculation to forbid OOTA executions. Our approach takes a different direction to provide an initial study of the runtime overhead of restricting compiler optimizations to eliminate out-of-thin-air behaviors.

    研究人员还提出了其目标是在接纳编译器优化的同时禁止凭空产生 (out-of-thin-air) 行为的内存模型 (memory models)。Jeffrey and Riely [2016]；Pichon-Pharabod and Sewell [2016] 提出了基于事件结构 (event structures) 的弱内存模型 (weak memory models)，事件结构是一组具有某种因果顺序和冲突关系的内存访问事件。与其关注一个候选执行 (candidate execution)，这些方法捕捉的是不同候选执行彼此之间如何关联并发生分歧。Kang et al. [2017] 提出了一种基于带有时间戳和承诺 (promises) 的操作语义 (operational semantics) 的内存模型 (memory model)，以禁止凭空产生 (out-of-thin-air) 行为。他们的方法引入了特殊的归约步骤 (reduction steps)，以允许线程执行一次写入，并带有一个可以在局部被验证的承诺 (promise)。Jagadeesan et al. [2010] 提出了一种用于 Java 的操作型内存模型 (operational memory model)，它基于一种推测 (speculation) 的概念来禁止 OOTA 执行。我们的方法则采取了不同的方向，对通过限制编译器优化来消除凭空产生 (out-of-thin-air) 行为的运行时开销进行初步研究。

    Researchers [Marino et al. 2011; Singh et al. 2012] have suggested stronger memory models, e.g., sequential consistency, in which out-of-thin-air behaviors are prohibited. They show that the cost is low when they implement such memory models on specialized hardware. Our approaches also explores stronger memory models than the existing C/C++ memory model; however, the constraints we impose in general are much weaker than the sequential consistency memory model. In addition, both of our approaches directly target existing widely-deployed commercial processor designs that implemented a relaxed memory model. Liu et al. [2017] have proposed a stronger Java memory model, which by default has sequential consistency semantics. They show that the overhead is arguably acceptable for server-side applications running on Intel x86 architectures.

    研究人员 [Marino et al. 2011; Singh et al. 2012] 提出了更强的内存模型 (memory model)，例如顺序一致性 (sequential consistency)，其中凭空产生 (out-of-thin-air) 行为被禁止。他们表明，当在专用硬件上实现此类内存模型 (memory model) 时，其成本较低。我们的方法也探索了比现有 C/C++ 内存模型 (memory model) 更强的内存模型 (memory model)；然而，我们通常施加的约束比顺序一致性内存模型 (memory model) 弱得多。此外，我们的两种方法都直接面向现有的、已广泛部署且实现了宽松内存模型 (memory model) 的商用处理器设计。Liu et al. [2017] 提出了一种更强的 Java 内存模型 (memory model)，其默认具有顺序一致性 (sequential consistency) 语义。他们表明，对于运行在 Intel x86 架构上的服务器端应用程序，这种开销可以说是可接受的。

    Zhang and Feng [2016] propose an operational memory model that is based on a replay mechanism to simulate speculation. Their model forbids some but not all OOTA behaviors. Demange et al. [2013]; Ševčík et al. [2013] propose TSO for C and Java, which is strictly stronger than our approach of preserving load-store ordering.

    Zhang 和 Feng [2016] 提出了一种基于重放机制 (replay mechanism) 来模拟推测 (speculation) 的操作型内存模型 (operational memory model)。他们的模型禁止了一些但并非所有 OOTA 行为。Demange et al. [2013]；Ševčík et al. [2013] 为 C 和 Java 提出了 TSO，这严格强于我们保持加载-存储顺序 (load-store ordering) 的方法。

    There is also work that benchmarks the performance of weak memory models. Ritson and Owens [2016] focus on investigating the cost of prohibiting out-of-thin-air behaviors on the Linux kernel. They inject identifiable assembly sequences into the compiler output and use binary rewriting techniques to test different instruction sequences that may prevent out-of-thin-air behaviors. Our work focuses on a more general-purpose approach which involves modifying existing compiler code generation process and comparing the result with the original compiler.

    也有一些工作对弱内存模型 (weak memory models) 的性能进行了基准测试。Ritson 和 Owens [2016] 重点研究了在 Linux 内核上禁止无中生有行为 (out-of-thin-air behaviors) 的代价。他们将可识别的汇编序列注入到编译器输出中，并使用二进制重写技术测试可能防止无中生有行为 (out-of-thin-air behaviors) 的不同指令序列。我们的工作则侧重于一种更通用的方法，该方法涉及修改现有编译器代码生成过程，并将结果与原始编译器进行比较。

    Hardware memory models generally do not allow out-of-thin-air behaviors since they respect a syntactic data and control dependencies, while traditional compiler optimizations could potentially introduce such behaviors [Boehm and Demsky 2014]. Our dependency-preserving approach defines a dependency notion that is close to that of the hardware and enforces the compiler to generate code that respects such dependencies.

    硬件内存模型 (Hardware memory models) 通常不允许凭空出现 (out-of-thin-air) 行为，因为它们遵循句法数据依赖 (data dependencies) 和控制依赖 (control dependencies)，而传统编译器优化 (compiler optimizations) 则可能引入此类行为 [Boehm and Demsky 2014]。我们保持依赖的方法 (dependency-preserving approach) 定义了一种接近硬件所采用的依赖概念，并强制编译器生成尊重此类依赖的代码。

    7 CONCLUSION

    Restricting compiler optimizations is a promising solution to eliminate out-of-thin-air behaviors. Our results show that on an ARMv8 processor the dependency-preserving approach has an average overhead of 3.1% and a maximum overhead of 17.6% on the SPEC CPU2006 C/C++ benchmarks, and that the load-store-order-preserving approach has no overhead on average and a maximum overhead of 6.3% on 43 concurrent data structures, which indicates that the approach deserves further consideration. There remain opportunities to further reduce overheads by implementing more sophisticated optimizations and by carefully auditing the compiler optimization passes we omitted.

    限制编译器优化 (compiler optimizations) 是消除凭空出现行为 (out-of-thin-air behaviors) 的一种很有前景的解决方案。我们的结果表明，在 ARMv8 处理器上，保持依赖关系的方法 (dependency-preserving approach) 在 SPEC CPU2006 C/C++ 基准测试上平均开销为 3.1%，最大开销为 17.6%；而保持加载-存储顺序的方法 (load-store-order-preserving approach) 在 43 个并发数据结构上平均没有开销，最大开销为 6.3%，这表明该方法值得进一步考虑。通过实现更复杂的优化以及仔细审查我们省略的编译器优化过程 (compiler optimization passes)，仍然有机会进一步降低开销。
